Workflow Inspector

This page replays one run of a workflow, step by step: where the item went, how its context (working memory) changed, and for each model agent exactly what it was given, what it did, what it returned and whether the host kept it. It says where every piece of prompt text came from.

Not recorded anywhere: Claude Code's own system prompt, the exact commands agents ran, and the messages the parent session sends when it resumes an agent. Lane A and lane C runs are scripted: their agents are test fixtures, GitHub is fake, and no model ran.

More: the seven layers, the caveats, and the words used here

A workflow is a map of states (briefing, building, verifying...). An item moves through it one step at a time: each step is an event, such as an agent finishing, a CI result or a person's tap. On each step the item's context (its working memory) can change, and the step can start actors: model agents (Claude Code subagents) or host code (posting a card, merging a PR).

For each model agent there are seven layers, top to bottom:

  1. Claude Code system prompt: never recorded by the harness, so it cannot be shown.
  2. Prompt (brief.md), and who wrote it: a person, the workflow file's author (instructions written into the workflow JSON), an earlier agent, or nobody (the engine's fill-in template around the actor's input).
  3. Added context (context.md): what the harness adds beside the prompt when the agent starts.
  4. Output schema: the shape its answer must have, as the agent was shown it.
  5. What it did: its tool calls, when a live capture exists.
  6. What the host stored as its result (result.json), with any fields the host added itself marked.
  7. Host check: whether the host stored the answer or sent it back, and what the workflow did next.

Honesty caveats.

  • The Claude Code system prompt is never recorded (layer 1).
  • Tool calls keep only the tool name, time, size and paths. The exact commands are not stored, only a hash of them.
  • When the parent session resumes an agent (for example because it finished without calling the return tool), the message it sends is not recorded. The prompt shown in layer 2 is then the agent's first message, not everything it was told; the page marks such agents "resumed, message not recorded".
  • Lane A and lane C runs are scripted scenarios: their "agents" are test fixtures (briefs and results typed into the test), GitHub is a fake server, and no model ran. They show what each design's engine would hand a real agent.
  • The context after each step is recovered by replay. The page says where replay did not match or failed.
  • Real runs from before workflows were pinned are shown with today's workflow file; the page says so on those runs.

Words used here.

event
Something that happened to the item: an agent finishing (xstate.done.actor.build means "the build actor finished"), a CI result, a tap. The first event, xstate.init, starts the item.
guard
A yes/no test on the item's context, named in the workflow JSON. A way out with a guard is taken only when the test holds.
needs
What must be true of the context to enter a state. The engine checks them like guards on every way in.
join
When everything inside a group state is done (it reached a final state), the group itself finishes and its own way out is taken.
invoke
A state starting an actor when the item enters it.
replay
Re-running the journal's events through the engine to recover the context, which the journal stores only as a hash.
hash check
A fingerprint comparison: equal hashes mean the bytes are identical.
brief
Three things share this word: the brief agent (the first actor, which writes instructions for the others), brief.md (any agent's prompt) and context.briefs (where the brief agent's output is kept).
